> **Goal（Locked）**：产出交付局文件区并通过 fresh 敌意审查与 fresh 验证。

## 一、Actor Registry

| Actor | 类型 | Assignment |
|---|---|---|
| goal-keeper（人类） | human | 异步终审：分类确认 ✓（已完成）；批准成军 ✓（已完成）；例外处理（待触发）；七件套终审（待触发） |
| coordinator | ai-orchestrator | 单写者：起草本 AOOS 与 DecisionRecord，撰写七件套，接受敌意审查反馈并修复，提交终审 |
| hostile-reviewer | ai-worker（fresh，无共享上下文） | 只读攻击：理论忠实性／四职能打穿真实性／并行治理可行性／死法遗漏／自举可执行性；判决三选一（ACCEPT / notes / REWORK） |
| verifier | ai-worker（fresh，无共享上下文） | 只读审计：AC 逐条合规 + 实测（自写脚本检查路径/交叉引用/格式）；只报告不修复，结论构成 Pre-Verified |

## 二、Role 要点

- **coordinator**：responsibility＝组织形成、七件套撰写、修复与综合；authority＝在 交付局/ 新建文件、登记注册表；constraints＝不改元组织规范、无缓存 active 化裁决权、产物必须经 fresh 复核。
- **hostile-reviewer**：responsibility＝以推翻草稿为任务；authority＝只读；constraints＝不修复、fresh 实例、无共享上下文。
- **verifier**：responsibility＝独立判定；authority＝只读＋可自写并运行检查脚本；constraints＝不修复、fresh 实例、结论只构成 Pre-Verified。

## 三、任务分解（波次）

- **波次 1（coordinator）**：落盘本 AOOS + DecisionRecord → 撰写 00–06 七件 → 交叉自检与元层一致性。
- **波次 2（hostile-reviewer，fresh）**：攻击七件套 → coordinator 修复并留痕（记入 §七）。
- **波次 3（verifier，fresh）**：AC 全量审计 → Pre-Verified 报告 → 提交 goal-keeper 终审。
- **后续（不属本组织范围）**：真实项目进入时，另按 05-路由决策表 成军项目军，本设计军验收即解散。

## 四、DecisionRecord（事前）

**决策：将成军局元组织实例化为软件交付领域（交付局），打穿产品/编码/质检/项目管理四职能，单名人类+多 AI 完成项目全生命周期并支持多项目并行。**

**维度（成功怎么判）**：① 七件套过 fresh 敌意审查与 fresh 验证；② 新会话仅凭文件区可自举；③ 真实项目可以「按交付局处理：<目标>」进入并成军；④ 带宽总账产生首组可记录读数。

**死法（概率×代价），6 条**：

1. **D3 判断带宽破产**：并行治理设计成空谈，单人类被触点淹没 → 对策：触点当量账本 + 三个可批量队列 + PENDING 安全停靠 + 超限动作序列（降并发→收窄作业面，永不降验证标准）。
2. **理论失真**：交付局规范与元组织规范冲突，或误引理论条款 → 对策：政策块逐字继承；冲突条款「元层优先」写入 00 §1；敌意审查设「理论忠实性」专维。
3. **名义打穿实际残留**：在交付局内以任何名义设立常设产品/开发/QA/PM 岗 → 对策：「无常设执行岗位」写入 00 §1 铁律；敌意审查专维；项目内只有门与模块所有权。
4. **需求稳定前提被侵蚀**：真实项目需求变动频繁，goal-lock 失效 → 对策：政策 goal-change-relock（变更＝重过目标闸）；变更账本；项目变更率超阈值即标记「前提失效」并重分批（阈值为 candidate）。
5. **协调者自身失效/上下文腐化（必含预演）**：coordinator 对元组织规范理解有偏，污染七件套且自检不可见 → 对策：本组织一切产物必须过 fresh 敌意审查与 fresh 验证；coordinator 无 active 化裁决权；自举协议不依赖记忆，一切状态在盘。
6. **假验证**：verifier 与 coordinator 共享上下文，或只读不跑 → 对策：fresh 实例派发；政策 verify-by-running；Verified 只能由人类授予。

**可逆性**：全部为新增文件，本体回退＝删除 交付局/ 目录；已扩散引用（注册表行、会话记录、记忆文件）需逐一回收。

**事前 Prediction**：
- P1：敌意审查发现 ≥5 处击穿，其中 ≥1 处属「理论忠实性」（即我对元组织规范的引用存在偏差）。
- P2：软件路由表至少 1 行被指「参数设定过早」（尚无真实项目数据）。
- P3：触点当量数字被指「缺乏实证依据」，须显式标 candidate 并附校准计划。
- P4：需求稳定前提的操作化条款（变更账本/阈值）被指不够具体。
- P5：敌意审查判决最可能为 notes（修复后通过）而非直接 ACCEPT。

## 五、Runtime Loop（含降级拓扑预置）

标准 AOOS 循环（Goal→分析→选人→授权→执行→验证→学习→重构）。

- **限流类**：敌意审查/验证子代理派发失败（环境故障）→ 重试一次；仍失败则停机留痕上报，不得跳过门（halt-not-silent）。
- **过滤类**：文件写入路径冲突或权限不足 → 停下上报，不得越出 交付局/ 边界写文件。
- **超界类**：敌意审查击穿数 >10 或判决 REWORK → 本波判超界 → 停机留痕上报 goal-keeper，不得自授权缩小范围。
